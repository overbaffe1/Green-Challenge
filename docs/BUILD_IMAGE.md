# Сборка и пуш образа: что работает, а что нет

Проверено 2026-10-18 в этой среде. Итог: **образ нужно собирать на машине с
Docker и доступом к реестру**; из песочницы и с GitHub-hosted раннера это не
получается.

## Что именно не получилось и почему

| Попытка | Результат |
| --- | --- |
| `docker` в песочнице | отсутствует; установить нельзя (нет доступа к демону) |
| GitHub-hosted runner, `docker pull aij-green-challenge.cr.cloud.ru/green-vla@sha256:317dc67f…` | 8 попыток за ~35 минут, каждый раз `failed to acquire network quota for blob pull` |
| Публичность образа | проверена: `GET /v2/` → 401 (нормально), манифест по digest → **200**; то есть образ публичный, режет именно квота загрузки блобов |

Это ровно то, что участники видят как `QUOTA_NOT_AVAILABLE` при `docker pull`
конкурсных образов. Организаторы несколько раз отвечали «проблема устранена»,
но ограничение по крайней мере для внешних сетей возвращается.

Вывод: собирать нужно там, откуда реестр отдаёт слои — на вашей GPU-машине или
на self-hosted раннере в той же сети. Workflow
`.github/workflows/build-image.yml` для этого и оставлен: он корректно
собирает, тестирует и пушит, но ему нужен раннер с доступом.

## Рабочий путь

```bash
# 1. авторизация в реестре, в который вы пушите
docker login cr.cloud.ru

# 2. сборка + smoke + пуш + submission.txt одной командой
REGISTRY=cr.cloud.ru/<ваш-неймспейс> ./tools/build_and_submit.sh
```

Скрипт:

1. проверяет Docker, GPU-рантайм и свободное место;
2. собирает от конкурсного образа, **пришпиленного по digest**;
3. запускает контейнер с `--network none` и проверяет, что `greenchallenge`
   импортируется, а `GC_SPEED=1.3` даёт шаг строки 1/39;
4. проверяет, что размер < 50 ГБ;
5. пушит и опрашивает реестр, пока манифест не станет доступен (защита от
   отправки во время незавершённого пуша — иначе платформа отвечает
   `No such file or directory: /opt/enroot/data/<id>_client`);
6. пишет `submission/submission.txt` с digest и валидирует формат.

Отдельные шаги, если нужен контроль:

```bash
BASE='aij-green-challenge.cr.cloud.ru/green-vla@sha256:317dc67f49de511e9fd0fb97fb27fefd3cd95125655c1410ac3956505edd6037'
docker build -f docker/Dockerfile --build-arg BASE_IMAGE="$BASE" -t cr.cloud.ru/<ns>:1.3 .
docker push cr.cloud.ru/<ns>:1.3
docker buildx imagetools inspect cr.cloud.ru/<ns>:1.3     # убедиться, что виден
docker image inspect --format '{{index .RepoDigests 0}}' cr.cloud.ru/<ns>:1.3
python tools/submission_file.py make --ref '@sha256:<digest>'
```

## Почему нельзя обойтись без конкурсного образа

Образ несёт чекпоинт GreenVLAv1.1, кэш Qwen3.5-0.8B, CUDA-ядра и два сервера
организаторов. Сборка «с нуля» — это torch+cu128, flash-attn и causal-conv1d
под sm_120, ~20 ГБ загрузок и часы компиляции; на 6-часовом раннере это лотерея,
а на 14 ГБ свободного диска — гарантированный провал. Поэтому наш Dockerfile
наследует конкурсный образ и добавляет только слой с `greenchallenge/`.

## Если реестр снова отвечает QUOTA_NOT_AVAILABLE

* повторить через 10–30 минут;
* тянуть по тегу, а не по digest (тег иногда отдаётся из кеша быстрее);
* убедиться, что не тянете параллельно несколько больших образов;
* если есть выбор — собирать на машине в сети `cr.cloud.ru`.
