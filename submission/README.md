# Что класть в «Загрузка решения»

**Файл:** [`submission.txt`](submission.txt) — обычный текст, **одна строка**,
только digest:

```
@sha256:317dc67f49de511e9fd0fb97fb27fefd3cd95125655c1410ac3956505edd6037
```

Сейчас в файле лежит **digest официального бейзлайна**. Это валидная, но
слабая заявка (≈15 очков из 88): платформа запустит образ организаторов, а не
ваш, и потратит суточный слот. Замените её на digest своего образа:

```bash
# после docker build + docker push
python tools/submission_file.py make --ref <ваш-registry>/green-challenge:1.3
python tools/submission_file.py check
```

`make` берёт digest из локального Docker (`docker image inspect`), поэтому
перезаписанный в реестре тег не попадёт в сабмит случайно. Если образа в Docker
нет, передайте digest явно: `--ref '@sha256:<64 hex>'`.

## Формат, который платформа точно принимает

| Поле | Значение |
| --- | --- |
| Строка | ровно одна: `@sha256:` + 64 шестнадцатеричных символа в нижнем регистре |
| Тег | **нельзя** — `green-vla:v1@sha256:…` даёт `INFRA_ERROR / rtx_status: INTERNAL_ERROR` через 2 минуты очереди |
| Путь к реестру | не нужен; организаторы просят присылать только digest |
| Пробелы, перевод строки в конце | допустим один `\n`; лишние пробелы лучше убрать |

Проверка формата — офлайн, без обращения к платформе:

```bash
python tools/submission_file.py check
# OK: submission/submission.txt -> @sha256:...
```

## Чем это подтверждено

Из официального треда конкурса (сентябрь–октябрь 2026):

* «В вашем случае вы передаете одновременно tag и digest образа. Необходимо
  убрать тег» — и после этого решение запустилось (участник `mitchell1743`,
  `mccullough8320`, `pacocha6731` — один и тот же диагноз трижды).
* «Если вы используете digest (@sha256:...), тег указывать не нужно. Digest
  однозначно ссылается на конкретный образ и не меняется при перезаписи тега.»
* Про публикацию полной ссылки: «не публикуйте полную ссылку на образ в общем
  чате… это может стать основанием для дисквалификации». Поэтому в файле только
  digest, а не путь к реестру.
* «Чистый txt, одна строка, без тега и полного пути» — формулировка участника,
  чья отправка baseline прошла валидацию.

## Как получить digest **нашего** образа

Собрать образ нужно на машине, у которой есть Docker и доступ к реестру: из
песочницы это невозможно (нет Docker; реестр `aij-green-challenge.cr.cloud.ru`
пускает только из своей сети — GitHub-раннер получил
`failed to acquire network quota for blob pull` восемь раз подряд).

Одна команда на вашей машине:

```bash
REGISTRY=cr.cloud.ru/<ваш-неймспейс> ./tools/build_and_submit.sh
```

Скрипт собирает образ от конкурсного (по digest), делает smoke-тест импорта и
конфига без GPU, пушит, **ждёт, пока реестр начнёт отдавать манифест**, и только
потом пишет `submission/submission.txt` с digest. `TAG`, `GC_SPEED` и
`BASE_IMAGE` можно переопределить; `DRY_RUN=1` печатает шаги без запуска,
`SKIP_PUSH=1` останавливается после сборки.

Проверка без пуша:

```bash
REGISTRY=x SKIP_PUSH=1 ./tools/build_and_submit.sh
DRY_RUN=1 REGISTRY=x ./tools/build_and_submit.sh   # только команды
```

## Порядок отправки

1. `docker build` → `docker push` в реестр, к которому у платформы есть доступ.
2. Дождаться **полного** завершения `docker push`. Отправка решения во время
   незаконченной загрузки даёт `[ERROR] No such file or directory:
   /opt/enroot/data/814_client` (реальный случай из треда).
3. `python tools/submission_file.py make --ref <ссылка с тегом>`.
4. `python tools/submission_file.py check`.
5. Загрузить `submission/submission.txt` в «Загрузка решения».
6. **Не удалять образ из реестра** до конца конкурса: организаторы могут
   пересчитывать сабмиты (прямой ответ в треде).

## Если платформа падает не по вашей вине

`INFRA_ERROR / rtx_status: INTERNAL_ERROR`, `RESULT_MISSING`, `RTX_UNAVAILABLE`,
зависание на «01. Очистка дискового пространства» — это инфраструктура
организаторов. В треде такие случаи разбирали десятки раз; лечение почти всегда
одно — повторить отправку, иногда после пересборки и повторного пуша образа.
По словам участника, столкнувшегося с `RTX_UNAVAILABLE`, повторная попытка
прошла без кулдауна, то есть неудачный запуск не съел суточный лимит.

`submission.baseline.txt` — копия baseline-digest отдельным файлом, чтобы
случайно не перезаписать страховочный вариант рабочей ссылкой.
